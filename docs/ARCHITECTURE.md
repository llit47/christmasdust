# Architecture

One Node.js 24 process serves Express and static ES modules. Built-in `node:sqlite` stores ratings and player history in separate files; no build step.
Steam discovery (10 minutes) collects AppID 10 / cstrike metadata in eight broad regional requests plus at most 25 global targeted requests: up to 20 exact map filters from `config/christmas-maps.json`, rotating round-robin through the full catalog with an in-memory cursor, plus at most five safe `name_match` terms. Strong/related configured terms rotate instead of permanently selecting the first five. If configured as weak terms, `winter` and `snow` alternate in one of those five slots; the remaining four probe strong/related identity. `snow` also finds `snowy` substrings. `holiday` is not winter-specific, `ice` matches unrelated substrings such as service/voice, and `frozen` is generic mod branding, so they do not consume this limited search budget. These searches never change classification strength. The map filter is defined by [Steam's server browser filter API](https://partner.steamgames.com/doc/api/isteammatchmakingservers); its behavior through the Web API endpoint has not been verified with a live key. Targets are fixed, bounded and never visitor-controlled. Capped results, unavailable maps and unindexed servers can still be missed. GameDig counterstrike16 queries (45 seconds) target classified candidates, a shared bounded pending pool and operator includes. Both jobs serialize through one coordinator; a busy job is skipped, never piled up. Public reads use the cached snapshot and local SQLite; they never query game servers.

Steam Web API is the runtime discovery source in `auto` mode when keyed and in `steam` mode. Without a key, `auto` monitors configured seeds and restored entries; `seeds` disables discovery. Legacy Master UDP remains isolated in its module/tests: production DNS failure no longer creates partial discovery, and public coverage contains no Master counters.

Endpoints merge by validated public IPv4 address; source markers remain internal and persist across refreshes. Admission sorts each discovery pass by current metadata: already-classifiable relevant candidates, unclassified targeted candidates, then broad samples. This happens before consuming `MAX_SERVERS`; relevant rows do not consume the shared 128 pending slots. If earlier cycles have filled `MAX_SERVERS`, a new classifiable relevant arrival can replace one unclassified, never-live-verified discovery candidate. The oldest pending admission is evicted first, with endpoint ID breaking timestamp ties. Curated/operator-included rows, classified rows and all previously successful live rows are protected; when no eligible pending row can make room, the arrival is dropped. Generic unclassified Web regional rows still do not enter the pool. Never-verified targeted candidates recycle after three failed live queries; compatible legacy snapshot rows retain their failure behavior. Successful complete non-matches retain the existing two-observation retirement grace.

New unclassified `name:winter` candidates admit at most two endpoints per normalized name across the current monitor, including promoted members. Normalization reuses the unchanged public same-name filter's Unicode/case/punctuation/spacing rules. This early cap preserves capacity against same-name winter farms. When this name cap blocks a new unclassified `name:winter` probe, it may replace stale live-verified winter-only members of that same normalized name. At full `MAX_SERVERS`, the probe may similarly replace a stale winter-only member to make room, even if the discovery names differ. Eligibility uses `lastSeenAt` beyond `STALE_AFTER_MS`, the live-winter-only signal, and no independent classifier match. Replacement chooses the oldest successful live timestamp, then endpoint ID. Fresh members, curated/includes and independent classification remain protected. All replacements are planned before applying them, so failed admission (including the 128 pending limit) preserves the original rows. Probes remain unclassified until successful live verification; same-name replacements keep the discovery bound at two. Independently classifiable Christmas/XMAS/catalog-map evidence and operator includes bypass the winter-name admission cap. Deliberate mirror sampling counts as dropped admission, without reporting an upstream outage.

The monitor has a separate live-observation rule: successful A2S responses with targeted `name:winter` provenance and a non-negated normalized whole `winter` token in the current name can promote `none` to `probable`, including on ordinary maps. It adds a zero-score `live-verified-winter-name` signal and reason; it does not change `classify()` weights or thresholds. Discovery alone, `name:snow`, lost winter names and query failures cannot grant promotion. Before committing each live batch, winter-only promotions are grouped by their normalized measured live name across the complete monitor, including endpoints outside scoped queries. At most two winter-only members retain protection per name. Fresh members, based only on `lastSeenAt` within `STALE_AFTER_MS`, outrank stale members. Among fresh members, existing members of that same live-name group keep priority across failed/incomplete responses; remaining ties use endpoint ID order, independent of query completion order. Steam discovery refreshes of `discoveredAt` cannot extend incumbent priority. Excess members are removed immediately to release query capacity. Curated/includes and independently classified Christmas/XMAS/catalog-map rows are exempt and do not consume the winter-only quota. Successful excess responses count as live admission rejections, not query failures.

Schema-1 snapshots preserve this signal plus `lastSeenAt`; restore rechecks the saved name and targeted source through classification before reconciling winter-only groups. Pre-fix over-cap groups retain the two most recently live members, then prefer fewer query failures and endpoint ID for ties; excess winter-only rows are removed before general capacity pruning. Curated/includes and independent classification remain exempt, with no snapshot schema change. Discovery refreshes preserve the last live winter observation, while complete live theme loss hides then retires the endpoint under the existing rules. Classification, 32-slot sanity, manifest filtering and duplicate grouping otherwise apply normally. Public reads never trigger discovery or live queries.

The classifier tokenizes normalized name, Steam tags, optional description and map. `x-mas` and `x_mas` normalize to `xmas`; unrelated substrings do not match. Exact strong catalog maps and explicit Christmas/Xmas naming yield high confidence. Exact probable catalog maps require positive seasonal name, tag or description evidence before receiving probable confidence. A generic snow/ice/winter map or weak seasonal text alone never qualifies through the classifier, even if a targeted query returned it; live-verified targeted winter identity uses the separate monitor rule above. The score and structured signals explain the outcome; curated inclusion remains an operator decision with its own confidence label. `config/christmas-maps.json` is a vetted map catalog: `strong` covers Christmas/New Year maps and `probable` covers verified winter maps. Initial entries have published CS 1.6 map pages: [de_christmas](https://gamebanana.com/mods/346635), [de_dust2_xmas](https://gamebanana.com/mods/83799), [awp_christmas](https://gamebanana.com/mods/87180), [de_dust2_christmas2](https://gamebanana.com/mods/83715), and [deathrun_jinglebells](https://gamebanana.com/mods/91007). This score describes Christmas and winter relevance only.

Discovery merges candidates, never replaces the entire cache. Partial regional or targeted success remains useful. Steam `gametype` tags remain trusted discovery evidence across GameDig name/map queries, which cannot observe those tags. A later Steam record with an explicit updated tag value replaces that evidence; an omitted tag field does not. A failed live query retains previous metadata and increments misses; three consecutive misses mark offline. Online is a last-observed state, not a guarantee. Cached data ages visibly. An automatic candidate is hidden after one complete observation with a non-matching name and map, then removed after a second consecutive complete non-match from discovery or a successful live query. Incomplete name/map responses and query failures do not count. Hidden candidates also expire after the configured retention period (seven days by default) without positive theme evidence, even if incomplete responses keep arriving. Other non-curated servers expire after that period without discovery or successful queries; the total candidate count is capped. Includes remain monitored regardless of theme; exclusions win over includes.

Identity-based duplicate grouping in the cached public snapshot groups endpoints only when fresh responses share a usable Steam server ID and the same normalized name, map, capacity, game folder/title, protocol and available stable A2S metadata (top-level GameDig version, tags, mod and security fields). GoldSrc servers often omit the ID from A2S_INFO, so the backend sends a bounded `getchallenge steam` UDP probe to the already validated endpoint and briefly caches valid identities; IDs such as `1` and failed probes cannot group servers. Under identity-based grouping, similar names, maps or player counts alone do not group endpoints. The separate repeated-name visibility heuristic below can still suppress public copies without establishing a shared identity. The shared recommended-ranking comparator picks one representative; its API row includes `duplicateCount` and `duplicateEndpoints`. Every endpoint remains in the internal monitor and persisted snapshot. Incomplete or stale A2S identity leaves endpoints separate, so grouping may disappear temporarily during query failures. Steam IDs are server-advertised evidence, not independently verified ownership; this grouping does not assess fake players or server farms.

A separate live manifest filter runs before identity deduplication. Three or more fresh, successful, complete A2S observations on distinct public IPs with exactly matching normalized manifests hide unestablished matching members from public results and totals. Operator-curated endpoints are exempt. An endpoint with prior fresh complete evidence for that same manifest below the three-IP threshold remains public; an initial three-IP cluster without such evidence is hidden entirely. The manifest includes name, map, current players, capacity, known bots, password, folder/game, protocol, version and available appId, tags and stable mod/security fields; it excludes endpoint addresses and server identities. Missing core fields, incomplete responses, failed queries and stale observations cannot supply a match. Legacy GoldSrc INFO may omit appId, which remains an explicit unknown; a missing version prevents a manifest fingerprint. Protection is recorded only after a completed live batch, using fresh successful observations; one established manifest fingerprint per endpoint is persisted and omitted from public results. Public reads never establish protection. Records stay monitored and persisted, and become visible again when the matching group falls below three distinct fresh IPs. This is a conservative exact-manifest heuristic, not proof of fake players; legitimate servers with identical manifests can also be hidden.

A separate repeated-name visibility filter runs after manifest filtering and before identity-based duplicate grouping. It compares normalized names across the remaining fresh, online, non-curated candidates without strong map evidence. Normalization folds Unicode forms, case, whitespace and punctuation; empty normalized names do not form clusters. At least five distinct eligible IP addresses with the same normalized name trigger suppression to exactly one deterministic public representative; multiple ports on one IP count once. Curated entries and servers with positive precomputed map signals of kind `known-strong-map` or `explicit` are exempt and do not contribute to the threshold. The filter reuses `classification.signals` rather than classifying maps during public reads. Among eligible fresh/responding members, fewer misses, available lower backend query latency, and a stable endpoint ID tie-breaker choose the representative. Suppressed copies do not contribute players to public totals. Every endpoint remains monitored and persisted, and each snapshot reevaluates visibility so shrinking clusters or diverging names/maps recover automatically. This heuristic does not create identity-based duplicate groups or add suppressed endpoints to `duplicateEndpoints`; it is not proof that a server is fake.

Steam Networking / FakeIP endpoints are unsupported. They require a distinct Steam networking resolution and query path and are intentionally rejected by the public IPv4 validator rather than sent ordinary GameDig UDP queries.

Snapshots use a versioned schema, temporary file, fsync, atomic rename and directory fsync. Startup restores the last snapshot before accepting traffic. Memory can continue serving if disk persistence fails, with degraded health. Readiness means initialization completed; freshness is reported separately so an upstream outage does not cause restart loops.

Detection config is versioned independently. Runtime loading can interpret the supported unversioned legacy schema without rewriting it. Native updates resolve the service's configured absolute detection path with staged `readConfig()`, then create and validate a version 2 candidate beside that file. The first migration durably retains the exact v1 bytes for manual rollback to pre-v2 releases; an existing valid backup is never replaced. The completed release and `current` pointer are flushed to disk before the candidate config is renamed and its directory is flushed. A crash may leave the new release with legacy config, which it understands; it cannot durably leave the old release with v2-only config. Before readiness and revision verification, failure restores the old config and snapshot before the old release. Once those checks pass, the deployment is committed.

Visitor country comes from a local MMDB lookup or an explicitly trusted proxy's sanitized CF-IPCountry. The API never returns visitor coordinates. The opt-in browser geolocation result remains in memory; Haversine distance is computed locally. Recommendation orders Christmas relevance first, then same-country, geographic distance when available, online state, available slots and population. Distance is approximate and never network ping. GameDig latency is the monitor-to-server query latency.

External adapters (discovery, query, GeoIP), storage and clock are injected for offline tests. The frontend uses text nodes for external metadata and builds Steam links only from validated endpoints.

## Player history

`PlayerStatsStore` is injected into Monitor independently of snapshot persistence. Each successful current response with an explicit valid player count records its first measurement per endpoint in `floor(timestamp / 300000) * 300000`; cached counts, missing fields and failed queries never produce samples. Real zeroes remain zero. Recording precedes retirement and public visibility filters, so repeated-name, manifest and identity-grouped endpoints still collect samples while monitored. History retains endpoint identity after removal, but never retains or expands the query set. SQLite errors skip further writes in that live batch and retry on the next; list behavior and last good metadata are unchanged.

`GET /api/player-history` accepts no body or endpoint selection. One batched SQLite read returns only current public representative IDs, sorted and bounded to 5000, with 48 half-hour means per ID; empty buckets are `null`. The aligned window includes the current partial half hour (its end is the next half-hour boundary), allowing recent samples to appear promptly. Each value averages available five-minute measurements; a partially measured half hour remains a mean, while a completely unmeasured one becomes a line gap. Duplicate endpoint histories are never summed or merged. `/api/servers` carries no history. API failures return 503 without affecting server reads.

The frontend independently fetches history at load, every five minutes while visible, and on a stale visible-tab return. It retains last good charts on fetch failure. Native DOM/SVG draws separate segments around null gaps, omits lines with fewer than two measurements, and uses zero-to-capacity Y scaling when available (otherwise zero-to-observed-peak). Accessible titles report average and peak of the displayed half-hour points. Charts occupy the same 30px count row: 60×24px desktop, 50×22px tablet, 54×22px mobile, with no extra population row. No history enters selection or ranking.
